# 따오기 분석 대시보드 설계

## 1. 목표와 범위

따오기(ddaogi)는 DOJ의 공식 API 없이 저장소의 mock 데이터를 읽어 유저 활동과 대회 결과를 분석해 보여주는 서드파티 웹서비스다. 이번 작업은 다음 두 화면을 완성한다.

1. `jtw7913`의 레이팅, 문제 풀이, 기타 통계를 보여주는 유저 정보 페이지
2. `DOJ Beginner Contest 4`의 문제별 분석과 rated 참가자 분포를 보여주는 대회 정보 페이지

요구사항에 적힌 순서를 따라 유저 정보 페이지를 먼저 완성하고 검증한 뒤 대회 정보 페이지를 구현한다. 두 화면은 공통 앱 셸, 디자인 토큰, 티어/레이팅 표현, 통계 유틸리티를 공유한다. 로그인, 실시간 DOJ 연동, 검색, 다른 유저·대회 데이터 수집은 범위에 포함하지 않는다.

## 2. 채택한 접근

Next.js App Router의 서버 컴포넌트를 기본으로 사용하고, 탭·차트·툴팁·상세 전환처럼 브라우저 상태가 필요한 작은 영역만 클라이언트 컴포넌트로 만든다. 서버 전용 loader가 `data/`의 Markdown과 JSON을 읽어 검증된 DTO로 정규화한 뒤 화면에 전달한다.

전체 화면을 클라이언트 컴포넌트로 만드는 방식은 구현 초기에는 단순하지만 데이터 로딩과 표현 책임이 섞이고 번들이 커진다. 데이터를 컴포넌트에 직접 하드코딩하는 방식은 mock 파일 변경에 취약하다. 따라서 서버 중심 구조가 데이터 출처를 명확히 유지하면서 SoC와 테스트 용이성을 가장 잘 만족한다.

## 3. 기술 기준

- Next.js 16.3.0 App Router, React 19.2.8, TypeScript strict mode를 사용한다.
- Tailwind CSS 4를 기본 스타일링 수단으로 사용한다.
- shadcn/ui 패턴의 Card, Badge, Tabs, Button, Tooltip, Table, ScrollArea, Skeleton 컴포넌트를 구축한다.
- 아이콘은 `lucide-react`, 데이터 시각화는 `recharts`를 사용한다.
- 클래스 조합은 `clsx`, `tailwind-merge`, `class-variance-authority`로 통일한다.
- 테스트는 Vitest, Testing Library, jsdom을 사용한다.
- `unknown`과 `any`를 데이터 모델에 사용하지 않는다. JSON 입력은 명시적 타입 가드로 검증한다.
- 컴포넌트 파일은 PascalCase, App Router 세그먼트는 kebab-case를 사용한다.
- 내보내는 주요 컴포넌트와 통계 함수에는 JSDoc을 작성한다.

## 4. 라우팅과 앱 셸

- `/`는 서비스 소개를 별도로 만들지 않고 `/users/jtw7913`로 리다이렉트한다.
- `/users/[handle]`은 현재 mock 데이터가 존재하는 `jtw7913`만 렌더링한다. 다른 handle은 `notFound()`로 처리한다.
- `/contests/[contestSlug]`은 `doj-beginner-contest-4`만 렌더링한다. 다른 slug는 `notFound()`로 처리한다.
- 상단 내비게이션은 따오기 워드마크, 현재 유저 링크, 현재 대회 링크를 제공한다.
- 페이지 본문은 넓은 데스크톱에서는 최대 너비 컨테이너, 모바일에서는 한 열 카드 구조를 사용한다.
- 다크 모드는 별도 토글 상태를 저장하지 않고 시스템 설정과 Tailwind `dark:` 스타일을 따른다.

## 5. 데이터 계층

### 5.1 원본 데이터

- `data/user_info.md`: 현재/max 레이팅, 랭킹, 참가 대회, 전체 대회 일정, 1등·퍼솔 횟수
- `data/result.json`: 문제별 모든 제출
- `data/difficulty.json`: 문제 난이도
- `data/contest_info.md`: 대회 기본 정보, 문제 난이도, FF
- `data/contest_score_board.json`: 참가자 순위, 문제 점수, 퍼포먼스, 대회 전 레이팅

### 5.2 정규화 경계

서버 전용 loader는 원본 파일을 읽고 다음 DTO를 만든다.

- `UserProfile`: handle, currentRating, maxRating, ratingRank, ratingPercentile, podiumCount, firstFullCount
- `ContestParticipation`: date, name, rank, performanceRating, ratingDiff, ratingAfter, rated, tierBefore, tierAfter
- `ProblemSummary`: id, title, difficulty, bestScore, maxScore, solved, submissions
- `Submission`: language, submittedAt, score, maxScore
- `ContestSummary`: slug, title, organizers, startAt, endAt, durationMinutes, participationType, ratedUpperBound
- `ContestProblem`: index, title, difficulty, firstFullHandle, firstFullTime, estimates
- `ScoreboardEntry`: rank, nickname, scores, totalScore, performance, rating

Markdown 파서는 고정된 제목과 표 헤더를 검사한다. JSON은 key와 필드 타입을 검사하며, 파싱할 수 없는 필수 값이 있으면 loader가 출처 파일명을 포함한 오류를 발생시킨다.

### 5.3 누락 데이터 정책

- `difficulty.json`에 없는 문제는 `Unrated`로 정규화하고 UI에서는 `U`로 표시한다.
- 프로필 이미지와 플랜카드 URL이 없으므로 이미지 슬롯은 유지하되, handle 이니셜 아바타와 로컬 CSS 그라디언트 플랜카드를 fallback으로 표시한다. 나중에 URL이 추가되면 같은 컴포넌트 입력으로 교체할 수 있다.
- 해결 수 랭킹은 한 유저의 데이터만으로 계산할 수 없으므로 숫자를 임의 생성하지 않는다. 총 만점 문제 수는 표시하고 랭킹 자리는 `집계 미제공`으로 명시한다.
- rated 계산에서 `performance`가 `-`인 참가자는 퍼포먼스 통계에서 제외한다. `rating`이 없는 참가자는 레이팅 사분위수와 예상 레이팅 계산에서 제외한다.

## 7. 유저 정보 페이지

### 7.1 프로필 헤더

플랜카드 영역 위에 아바타, `jtw7913`, 현재 칭호, 현재 레이팅을 배치한다. 현재 1429와 max 1429, 89등, top 31.3%를 한눈에 비교할 수 있는 통계 카드로 제공한다. 플랜카드는 장식 배경 역할만 하며 텍스트 대비를 유지한다.

### 7.2 레이팅 탭

- `레이팅`과 `퍼포먼스` 세그먼트 버튼으로 같은 차트 영역의 series를 전환한다.
- 레이팅 차트의 y축 배경은 칭호 구간별 수평 band로 채운다.
- 점에 hover/focus하면 대회명, 날짜, 대회 후 레이팅 또는 퍼포먼스, diff, 순위를 표시한다.
- 최초 레이팅 +1200을 시작점으로 두고 rated 대회 diff를 누적하여 각 대회 후 레이팅을 계산한다.
- 참가 대회 표는 최신순이며 날짜, 대회명, 순위, 퍼포먼스, diff, 티어 변화를 보여준다. unrated의 퍼포먼스·diff와 티어 변화 없음은 `-`로 표시한다.
- 모바일에서는 표를 가로 스크롤하며 핵심 열을 유지한다.

대회 스트릭은 `user_info.md`의 전체 대회 목록 순서가 좌표축이다. 참가한 대회는 초록색 셀, 미참가는 중립 셀로 표현한다. 연속한 대회 인덱스를 기준으로 현재 연속과 최장 연속을 계산하며, 셀 tooltip에는 대회명·날짜·참가 여부를 표시한다.

### 7.3 문제 탭

- 각 문제의 최고 제출 점수가 만점 이상이면 만점 문제, 아니면 미만 문제로 분류한다.
- 두 목록은 난이도 축약 배지와 말줄임 제목을 보여준다. 링크는 `https://doj.kr/ko/problems/<id>`를 새 탭에서 연다.
- 모든 문제의 tooltip은 전체 제목을 보여주고, 미만 문제는 최고 점수/만점도 함께 보여준다.
- 문제 풀이 스트릭은 최초 만점 제출의 날짜를 기준으로 달력 heatmap을 만든다. 셀에는 그날 처음 만점 받은 문제 수를 표시하고 현재·최장 연속 일수를 계산한다.
- 총 만점 문제 수와 랭킹 상태를 상단 통계 카드에 표시한다.
- 난이도 도넛은 기본 상태에서 U/B/S/G/P/D/R 그룹을 보여준다. `자세히 보기`를 누르면 Bronze V부터 Ruby I까지 세부 분포로 전환한다.
- 범례에는 그룹별 해결 수와 전체 대비 비율을 표시한다. 데이터에 전체 문제 수가 없어 “해당 난이도의 모든 문제 해결” 여부는 판정할 수 없으므로 완료 표시를 임의 생성하지 않고, 전체 문제 수가 제공될 때만 초록색 완료 마크가 나타나는 인터페이스로 구현한다.

### 7.4 기타 정보 탭

- 전체 215개 제출을 언어별로 집계한 도넛과 건수·비율 범례를 표시한다.
- `pypy3`, `python3`, `cpp17`, `cpp20`, `custom-json`을 사용자 친화적 레이블로 변환한다.
- 대회 1등 횟수와 퍼솔 횟수 카드, 총 제출 수, 사용 언어 수를 함께 표시한다.

## 8. 대회 정보 페이지

### 8.1 대회 헤더

대회명, 시작·종료 시각, 제한 시간 100분, rated 상한 2400, 참가 타입 `일반`, 운영진을 보여준다. 참가 타입에는 일반이 동시 시작 방식이고 window는 개최 시간 안에서 개인별 시작 후 제한 시간만큼 응시하는 방식이라는 설명 tooltip을 제공한다.

### 8.2 rated 참가자 사분위수

유효한 대회 전 rating을 오름차순으로 정렬하고 선형 보간으로 Q1, 중앙값, Q3를 계산한다. 현재 mock 데이터의 검증 기준값은 Q1 1261, 중앙값 1452, Q3 1815다. 최소–Q1–중앙값–Q3–최대를 한 수평 분포 카드에 배치하고 각 지점에 칭호 색을 적용한다.

### 8.3 문제 분석

문제 A–I는 데스크톱에서 비교가 쉬운 테이블로, 모바일에서 한 문제씩 읽기 쉬운 카드로 표시한다. 두 표현 모두 문제명, 난이도, FF handle·시간, 예상 레이팅 네 값을 제공한다. FF가 없는 문제는 `아직 없음`으로 표시한다.

예상 레이팅은 다음 규칙으로 계산한다.

1. 숫자 rating이 있는 참가자만 선택한다.
2. 각 문제와 25%, 50%, 75%, 100% 기준마다 해당 점수 이상 획득한 참가자를 선택한다.
3. 선택된 참가자의 대회 전 rating 중앙값을 구하고 10 단위로 반올림한다.
4. 높은 점수 기준의 결과가 낮은 점수 기준보다 낮아지면 앞 기준값으로 올려 단조 증가를 보장한다.
5. 해당 참가자가 없으면 `-`로 표시한다.

이 수치는 공식 난이도나 실력 예측이 아니라 현재 mock scoreboard에서 계산한 추정치임을 UI에 명시한다.

## 9. 디자인과 상호작용

전체 분위기는 흰색/슬레이트 배경과 얇은 경계, 넉넉한 여백을 기반으로 하고, 따오기 브랜드 포인트로 주황색과 청록색을 제한적으로 사용한다. 다크 모드는 짙은 슬레이트 배경과 낮은 채도의 경계로 전환한다. 카드마다 과한 그림자나 그라디언트를 반복하지 않는다.

차트는 색상만으로 상태를 구분하지 않고 텍스트 레이블, 수치, 패턴 또는 마커를 함께 제공한다. 탭·버튼·링크·tooltip trigger는 키보드로 접근할 수 있고 명확한 focus ring을 가진다. 애니메이션은 짧은 opacity/transform 전환만 사용하며 `prefers-reduced-motion`을 존중한다.

## 10. 오류와 빈 상태

- loader 오류는 개발 환경에서 원본 파일과 필드명을 포함해 실패하게 하여 잘못된 mock 데이터를 숨기지 않는다.
- 지원하지 않는 handle/slug는 404로 처리한다.
- 차트 series가 비어 있으면 축만 그리지 않고 설명이 있는 빈 상태 카드를 렌더링한다.
- 목록이 비면 성공 상태와 미시도 상태를 구분하는 문구를 사용한다.
- 외부 DOJ 문제 링크에는 `target="_blank"`와 `rel="noreferrer"`를 적용한다.

## 11. 테스트와 완료 기준

- 대회 문제 FF 없음과 추정치 안내

### 통합·시각 검증

- `npm run lint`, `npx tsc --noEmit`, 전체 테스트, `npm run build` 모두 성공

## 12. 구현 분할

설계는 하나의 서비스로 공유되지만 구현 계획은 검토 가능한 두 단계로 나눈다.
